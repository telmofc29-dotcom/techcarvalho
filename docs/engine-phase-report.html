The finding that outranks everything I built

All 195 discoveries have exactly one evidence row from exactly one publisher. Zero have independent corroboration.

That is the real reason no brief clears the evidence bar. It is not that my threshold is harsh — it is that the research stage has never gone back for a second source. Discovery works; corroboration has never run. Every brief in your backlog is one feed item, restated.

I did not work around this. Lowering the bar to two sources from one publisher would have manufactured exactly the false confidence the whole system is built to refuse. It needs fixing at the research stage, and it is the single highest-value thing left to do.

01

Owner queue

/admin/engine is now Today: one ranked list of what needs a human, drawn from four tables, with the reason on the row and the action inline. The fourteen job views moved behind Engine details — consolidating the front door cost nobody the detail behind it.

/admin now leads with engine status and a needs-attention count. Before this it showed eight tables of counts and did not link to /admin/engine at all, so you could open the dashboard daily and never learn anything was waiting.

Three things it deliberately refuses to do: surface all 130 pending records (that is an engine statistic, not a to-do list); show urgency as a number (there is no measured demand — a sort key dressed as a score is fake precision); and let a failed read look like an empty queue. "Nothing needs your attention" is the most reassuring thing this app can say, so it can never say it because a query broke.

Rights decisions rank above everything, not on editorial grounds — they are the only work here the engine is structurally forbidden to ever resolve, so they must not queue behind work merely waiting for a human today. Ties break oldest-first, so a repeatedly-skipped item cannot grow a permanent tail.

A bug this caught before it shipped

registrableDomain() takes a host, not a URL. Passing a full URL silently yields junk — https://news.bbc.co.uk/a became "co.uk/a" — and because junk values differ from each other they counted as separate publishers. That fails open: inflated independence is exactly what lets an under-sourced brief reach "ready". Caught by the single-publisher test before it ever ran on your data.

03

One-click package

The package states every consequence on one screen and asks once. Approving then assembles immediately for that brief, rather than leaving it for a nightly tick you would have to remember to come back for.

It is the same path, not a parallel one: assembleDraft, proposeSeo, proposeSlug and the engine_assemble_draft RPC are each the exact function the nightly stage calls. Nothing is a second implementation that could drift.

The load-bearing distinction is "already true" versus "will be created". "Apple exists" and "iPhone 18 will be created" look alike on a checklist and are opposite facts. A product your brief names but the catalogue lacks is reported as a warning, never as something approval creates — a product needs specs, and specs are never invented to fill a shell.

A clearance is only claimed when it was actually computed. If the published-content read fails, the package says "could not be checked", never "no overlap found". A false duplication clearance is how a site starts competing with itself.

The publishing boundary, proven rather than asserted

engine_assemble_draft is SECURITY DEFINER and hard-wires status='draft'. It cannot be made to publish from an admin session with any argument. The live production test asserts the created row is a draft rather than trusting it.

The database holds zero discoveries and zero evidence rows about an iPhone 18. Apple exists; iPhone 17 Pro exists; nothing else. The verdict:

  • No article is produced, and the gap is recorded so it keeps looking
  • CAN BUILD: NO

That last line is new, because the test found a real defect.

What the test caught

The package originally reported CAN BUILD: YES for a brief with zero sources and zero verified facts — the only blockers were duplication, re-assembly and a missing slug. Worse, "0 sources" and "0 verified facts" rendered with green ticks: counts marked by the fact that they had been counted rather than by what they said.

Your queue would never have shown that brief — but the package page is reachable by URL, and reachable-by-URL is a real path a stale tab takes. The rule is now an invariant inside the package itself: it can only build what the quality gate would admit, with a test pinning the two gates together.

Reproduce it any time: npx tsx scripts/iphone-18-package.ts. Read-only.

05

Engine modes

MANUAL / ASSISTED / AUTOMATIC per stage, enforced in the tick — MANUAL stages do not run, and the run log says "you turned this off" rather than reporting a circuit-breaker reason that would send you somewhere unhelpful.

The decision that matters: AUTOMATIC is a capability declared per stage, not a setting accepted everywhere. "Automatic means skip the human" is wrong, because for most stages the human is not a rubber stamp — they supply a judgement the engine cannot make.

StageAutomaticWhy

AUTOMATIC_CAPABILITY is a total record over the stage list: adding a stage without answering the automation question fails to compile. "Nobody thought about it" must not arrive in production as an enabled automation.

Resolution fails closed in every direction — garbage, absent, and unavailable-AUTOMATIC all become ASSISTED — and a test asserts nothing ever fails closed to MANUAL, which would look like the engine breaking. No mode can publish, in any combination.

06

Homepage, rotation, trending, overrides

Most of this already existed and rebuilding it would have been the duplication you forbade. I verified it rather than replacing it.

trending.ts ranks on recency with a per-type half-life — news 48h, comparisons 3 weeks, guides and troubleshooting ~6 weeks — plus cluster centrality and a small hero tie-breaker. So news already rotates and evergreen already decays differently, exactly as you asked.

It deliberately reads no analytics at all, and the reason is sharper than "sparse data": analytics_daily_rollups and engine_trends are admin-only under RLS, and RLS denies by returning zero rows, not an error. Querying them from the public path would look exactly like "nothing is popular" — forever, silently. That is the deterministic fallback you asked for, and it was already the design.

visual-variety.ts and homepage-sections.ts already enforce media and category diversity. Nothing fabricates popularity.

What was genuinely missing: an override that ends

Today a pin is permanent until you delete it. That is the "don't make me manage the homepage every day" problem — the natural use of a pin is temporary, the schema cannot express temporary, so every pin becomes a small permanent debt and the homepage rots around it.

The pending migration adds starts_at/ends_at and a boost mode (boost raises a score and lets ranking still decide; a pin forces a position), plus an _active view so an expired override becomes indistinguishable from no override, with no ranking code aware windows exist.
